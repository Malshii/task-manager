# Task Manager

A small full-stack task manager. A NestJS REST API stores tasks in memory, and a Next.js web app lets you create, edit, delete, filter and sort them.

## Tech stack

| Part | Stack |
| --- | --- |
| `api/` | NestJS 10, TypeScript (strict), class-validator / class-transformer, @nestjs/config, Jest + supertest |
| `web/` | Next.js 16 (App Router), React 19, TypeScript (strict), Tailwind CSS 4, shadcn/ui (Radix), Sonner toasts |

```
.
├── api/   NestJS REST API (port 3001)
└── web/   Next.js frontend (port 3000)
```

## Prerequisites

- **Node.js v20.19.0** (other Node 20.x releases should work; this is the version it was built and tested with)
- **npm 10.8.2** (ships with Node 20.19.0)

Check with `node -v` and `npm -v`. You do not need the Nest CLI installed.

## Getting started

Run these from a fresh clone. You need two terminals, one for each app.

### 1. Install dependencies

```bash
cd api
npm install
cd ../web
npm install
cd ..
```

### 2. Environment files

Copy each app's example file. The API reads `api/.env` and Next.js reads `web/.env.local`.

macOS / Linux:

```bash
cp api/.env.example api/.env
cp web/.env.example web/.env.local
```

Windows (PowerShell):

```powershell
Copy-Item api/.env.example api/.env
Copy-Item web/.env.example web/.env.local
```

Windows (Command Prompt):

```bat
copy api\.env.example api\.env
copy web\.env.example web\.env.local
```

The defaults work as-is, so you only need to edit these files to change a value.

| File | Variable | Default | Meaning |
| --- | --- | --- | --- |
| `api/.env` | `PORT` | `3001` | Port the API listens on |
| `api/.env` | `WEB_ORIGIN` | `http://localhost:3000` | The one origin allowed by CORS |
| `web/.env.local` | `NEXT_PUBLIC_API_URL` | `http://localhost:3001` | Base URL of the API |

The API loads `.env` from the directory you start it in, so run it from `api/` as shown below. A variable set in your shell takes priority over the file. If you change `PORT`, also change `NEXT_PUBLIC_API_URL` to match. Restart each app after editing its env file.


### 3. Start the backend (terminal 1)

```bash
cd api
npm run start:dev
```

The API is ready when you see `Nest application successfully started`. It listens on <http://localhost:3001>.

### 4. Start the frontend (terminal 2)

```bash
cd web
npm run dev
```

### 5. Open the app

- Web app: <http://localhost:3000>
- API: <http://localhost:3001/tasks>

## Using the app

- **New task** opens a form (title is required, max 200 characters).
- **Edit** opens the same form pre-filled. Clearing the description or due date removes it.
- **Delete** asks for confirmation first.
- The **status filter** and **Due date** sort toggle sit above the table. Tasks without a due date always sort last.

## API reference

Base URL: `http://localhost:3001`. Requests and responses are JSON.

### Task object

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | UUID, generated by the server |
| `title` | string | Required, non-empty, max 200 characters |
| `description` | string | Optional |
| `status` | `"TODO"` \| `"IN_PROGRESS"` \| `"DONE"` | Defaults to `TODO` |
| `dueDate` | string | Optional ISO 8601 date, e.g. `2026-12-01` |
| `createdAt` | string | ISO datetime, set by the server |

### Endpoints

| Method | Path | Success | Errors |
| --- | --- | --- | --- |
| `GET` | `/tasks` | 200, array of tasks | |
| `GET` | `/tasks/:id` | 200, task | 404 |
| `POST` | `/tasks` | 201, created task | 400 |
| `PATCH` | `/tasks/:id` | 200, updated task | 400, 404 |
| `DELETE` | `/tasks/:id` | 204, no body | 404 |

### Examples

**Create a task**

```bash
curl -X POST http://localhost:3001/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Write docs","description":"README","dueDate":"2026-12-01"}'
```

```json
{
  "title": "Write docs",
  "description": "README",
  "dueDate": "2026-12-01",
  "id": "0345d52c-7a43-4047-be33-0f0bd0faf55e",
  "status": "TODO",
  "createdAt": "2026-11-12T14:47:00.431Z"
}
```

**List tasks**

```bash
curl http://localhost:3001/tasks
```

Returns `200` with an array of task objects (`[]` when there are none).

**Update a task**

Send only the fields you want to change.

```bash
curl -X PATCH http://localhost:3001/tasks/<id> \
  -H "Content-Type: application/json" \
  -d '{"status":"DONE"}'
```

Update rules:

- `title` and `status` may be omitted, but if sent they must be valid. `null` is rejected with 400.
- `description` and `dueDate` accept `null` to clear the value, for example `{"dueDate":null}`.
- An empty body `{}` changes nothing and returns 200.

**Delete a task**

```bash
curl -i -X DELETE http://localhost:3001/tasks/<id>
```

Returns `204 No Content`.

### Errors

Errors use NestJS's standard shape.

**400 Bad Request**: validation failed. `message` lists every problem.

```bash
curl -X POST http://localhost:3001/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"","foo":1}'
```

```json
{
  "message": ["property foo should not exist", "title should not be empty"],
  "error": "Bad Request",
  "statusCode": 400
}
```

400 is returned for: a missing or empty title, a title over 200 characters, an invalid `status`, an invalid `dueDate`, `null` for `title` or `status` on update, and any property that is not part of the task model.

**404 Not Found**: no task with that id.

```bash
curl -i http://localhost:3001/tasks/does-not-exist
```

```json
{
  "message": "Task does-not-exist not found",
  "error": "Not Found",
  "statusCode": 404
}
```

On Windows PowerShell, use `curl.exe` instead of `curl` (which is an alias for a different command) and escape the quotes in the JSON, or use Git Bash.

## Design decisions

**In-memory storage.** Tasks live in a `Map` inside `TasksService`. This keeps the project runnable with no database to install or configure, and the service is the only place that touches storage, so it could later be swapped for a repository backed by a database without changing the controller. Trade-offs: all data is lost when the API restarts, it cannot be shared across multiple API instances, and there is no pagination or persistence guarantee.

**Validation at the edge.** A global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) validates every request body against the DTOs, so the service can trust its input. Unknown properties are rejected rather than silently dropped. The pipe is configured once in [api/src/app.setup.ts](api/src/app.setup.ts) and shared by `main.ts` and the e2e tests, so tests run with the same validation as production.

**Explicit update DTO.** `PartialType` makes every field `@IsOptional()`, which also skips validation for `null`, so `{"title": null}` would have been accepted. `UpdateTaskDto` is therefore written out by hand: `title` and `status` use `ValidateIf(v => v !== undefined)` so only an omitted value skips validation, while `description` and `dueDate` deliberately accept `null` as "clear this field". Cleared values are stored as absent, not `null`.

**Client-side filtering and sorting.** Filtering by status and sorting by due date happen in the browser, because the whole list is already loaded and the data set is small. With a real database and many tasks this would move to query parameters on `GET /tasks`.

**Dates.** `dueDate` is treated as a calendar date and displayed in UTC so it never shifts by a day across time zones; `createdAt` is a timestamp shown in local time.

**Small, single-purpose components.** The page owns all state and API calls; `TaskTable`, `TaskFormDialog`, `DeleteTaskDialog`, `StatusBadge` and `TaskToolbar` are presentational. The create and edit flows share one form dialog.
